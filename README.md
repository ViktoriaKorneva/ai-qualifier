# AI-квалификатор входящих

Бот, который принимает поток входящих обращений, отвечает на типовые вопросы
по базе знаний клиента, собирает анкету, отсекает нецелевых по правилам,
напоминает о недоделанном шаге и передаёт менеджеру уже готового лида.

> **Учебный прогон.** Клиент «Смена» (сервис подработок) — гипотетический,
> данные придуманы для тренировки. Реального заказчика с такими условиями нет.
> Прототип собран по ТЗ реального заказа с FL.ru как тренировка перед откликом.

## Запуск

```powershell
python run.py                     # диалог в консоли
python serve.py                   # веб-демо на http://127.0.0.1:8000
python tests/run_tests.py         # прогон всех наборов
python tests/run_tests.py parabola   # только вторая ниша
python tests/run_tests.py -v      # то же, с расшифровкой каждого диалога
python tests/run_api_tests.py     # проверки веб-адаптера
```

Нужны Python 3.10+, `pyyaml` и `requests`. Модель необязательна: без ключа
бот работает на правилах и базе знаний, свободные вопросы честно уходят человеку.

В диалоге работают служебные команды: `/time 3` сдвигает время на 3 часа
(чтобы показать напоминание, не ожидая три часа), `/quit` завершает и сохраняет лида.

## Что бот умеет

- **Забирает всё, что сказано, из любой реплики.** «Светлана, 23, Заречный,
  89001234567» одной строкой — профайл заполнен целиком, ни одного лишнего вопроса.
- **Не переспрашивает то, что уже знает.** Данные, названные не в свою очередь,
  не теряются, а ждут своего поля.
- **Отвечает на вопрос посреди анкеты** и возвращается к тому месту, где прервались.
  Человек спрашивает про оплату, когда захочет.
- **Принимает исправления:** «ой, я перепутал, мне 19» меняет уже записанное поле,
  а не уезжает в тот вопрос, который бот задал последним.
- **Показывает собранное перед передачей** и даёт поправить. Подтверждению
  неполной анкеты не верит.
- **Разбирает живые ответы:** «меня зовут Светлана», «2003» вместо возраста,
  телефон в любом формате, «в заречном» вместо «Заречный».
- **Отсекает по жёстким правилам** — вежливо и с объяснением причины.
  Правило срабатывает на поле независимо от того, когда оно заполнено.
- **Различает сказанное и посчитанное.** «2003» превращается в возраст, но
  помечается как выведенное — и отсев по такому значению не выносится.
- **Не выдумывает.** Сначала база знаний, потом модель со строгим запретом
  добавлять факты, потом честное «передам координатору». Обещать канал связи
  или другой финал сценария модели запрещено отдельным правилом.
- **Отвечает ролью, а не одним голосом.** Про график отвечает координатор смен,
  про договор и выплаты — специалист по оформлению.
- **Уводит человеку** конфликтные темы сразу, на любом шаге. И того, кто
  не отвечает ни на один вопрос, — вместо бесконечного круга уточнений.
- **Считает лида:** горячий / тёплый / холодный с прозрачным баллом.

## Профайл вместо очереди вопросов

Ключевое решение: бот хранит не номер текущего вопроса, а **состояние данных**.

```text
было:  question_index = 2        → «сейчас спрашиваю телефон»
стало: Profile(values, deferred) → «знаю имя и возраст, не знаю телефон и район»
```

Разница видна на первой же живой реплике. Счётчик забирает из
«Светлана, 23, Заречный, 89001234567» только имя и идёт спрашивать возраст,
который ему уже назвали. Профайл забирает все четыре поля.

Порядок вопросов из конфига остаётся — но как порядок по умолчанию, а не как
рельсы. Поле, от которого кандидат дважды уклонился, откладывается, и бот
возвращается к нему позже.

Метод взят из урока 17-01 курса УИИ (архитектура с ветками и блоками):
профайл — это информационное поле, а не список вопросов.

Что сканируется из свободной реплики и в каком порядке — от самого надёжного
признака к самому рискованному, с вырезанием найденного из остатка:

```text
1. телефон  — жёсткий паттерн российского мобильного
2. район    — сравнение с закрытым списком из конфига
3. возраст  — «28 лет» или одинокое двузначное число в остатке
4. имя      — только по маркеру «меня зовут» либо одиноким словом
```

Что не опознано уверенно — не угадывается: бот переспрашивает. Неверные данные
в карточке лида дороже лишнего вопроса.

## Сказанное и посчитанное — разные вещи

Часть значений бот выводит сам. «2003» — это не возраст, а год рождения, и
возраст из него получается приблизительный: до дня рождения человеку на год
меньше, а дня рождения мы не знаем.

Раньше такое значение ложилось в профайл неотличимо от названного вслух — и по
нему срабатывал отсев. То есть бот **отказывал живому человеку по цифре, которую
тот не называл.**

Теперь у поля есть источник:

```text
values["age"] = "23"        значение
derived        = {"age"}     посчитали мы, а не сказал кандидат
notes["age"]                 «вычислен из года рождения 2003: фактически 22 или 23»
```

Правила при этом:

- отсев по выведенному значению **не выносится никогда** — reject понижается до
  флага, и решение принимает менеджер;
- пометка едет в выгрузку отдельной колонкой `derived_fields` и в флаги, чтобы
  догадка не выглядела фактом;
- как только кандидат называет значение сам («я перепутал, мне 19»), пометка
  снимается и правила работают как обычно.

Границы года рождения считаются от текущего года, а не от вписанной константы:
захардкоженный год тихо начинает врать в новогоднюю ночь, и ни один тест
этого не заметит.

Метод из урока 17-02 курса УИИ: там агент вывел «9 лет» из «третий класс»
и записал в карточку клиента как данные.

## База знаний разбита по ролям

Раздел базы — это **адресация роли**, а не оглавление товара:

```text
work_conditions  → координатор смен          (график, точки, обучение)
money_and_docs   → специалист по оформлению  (ставки, выплаты, договор, самозанятость)
```

Вопрос сначала маршрутизируется в раздел, и в модель уходит только он — вместе
с описанием роли, от лица которой идёт ответ. Не вся база и не один общий голос.

Смысл не в экономии токенов, а в интонации: про деньги и документы у человека
больше всего тревоги, и там нужен ответ конкретный и цифрами, а не та же
анкетная реплика. Готовые ответы из базы от роли не зависят — их написал
заказчик.

Метод оттуда же: разделы базы урока кормили соответствующих агентов промта.
Агентская схема бесполезна, если база собрана как каталог.

## Этапы диалога

```text
приветствие → сбор профайла → [предложение] → проверка собранного → запись → передача
                    ↑                                │
                    └────────────── правка ──────────┘
```

Этап предложения включается наличием секции `proposal` в конфиге. Её нет —
диалог остаётся прежним, как у «Смены».

## Вторая ниша: центр подготовки к ЕГЭ и ОГЭ

`clients/parabola.yaml` — вымышленный образовательный центр. Ниша выбрана
затем, что в ней у решения появляется задача, которой не было у сервиса
подработок: **не обещать того, что не сбудется.**

Если стартовый уровень и срок до экзамена не сходятся с заявленной целью,
агент не отказывает и не закрывает диалог — он честно говорит, что цель под
вопросом, предлагает диагностику и отдаёт менеджеру расчёт, а не эмоцию.
Правило описано в конфиге числами, а не оставлено на усмотрение модели:

```text
разрыв        = балл цели − балл стартового уровня
нужно месяцев = разрыв × months_per_step
сработало     = осталось месяцев < нужно
```

Проверяется в обе стороны. Ложное срабатывание здесь дороже несработавшего:
агент, усомнившийся в достижимой цели, отговаривает платящего клиента.

Что эта ниша потребовала от ядра — шесть правок, все обобщающие:

| Правка | Зачем ниша её потребовала |
|---|---|
| обязательные и желательные поля | предложение делается после двух ответов, а не после полной анкеты |
| фазы вопросов и этап предложения | контакт спрашивают после предложения, а не до |
| вычисляемые поля (`computed`) | срок до экзамена считается из класса и системной даты |
| составные правила (`combined_rules`) | реалистичность цели зависит сразу от трёх полей |
| тип поля `scale` | «еле тянет» — это «слабый», а «десятый» — это «10» |
| тип поля `multi` | предметов всегда несколько |

Конфиг «Смены» при этом не изменился ни на строку, и его 34 сценария
остались зелёными: конфиг без `required`, фаз, `computed` и `combined_rules`
работает ровно как раньше. Обещание «новый клиент = новый YAML» в чистом виде
не выдержало — но правки добавили ядру возможности, а не знание про экзамены.

**Честные границы второй ниши:**

- Срок до экзамена только вычисляется из класса. Названный словами («до ЕГЭ
  полгода») не разбирается — поле не спрашивается и не сканируется.
- Балл распознаётся числом (`ranges`) и несколькими словесными формами.
  «Восемьдесят пять» словами не разбирается.
- Подбор интенсива зависит от текущей даты и в августе не проявляется:
  правило срабатывает, когда до экзамена меньше пяти месяцев.
- Проходные баллы вузов агент не называет никогда и отправляет в правила
  приёма. Это не пробел базы, а требование: придуманная цифра — враньё.

## Архитектура

Всё, что меняется от клиента к клиенту, живёт в конфиге и адаптерах, а не в коде.

```text
clients/*.yaml         вопросы, тексты, правила, база знаний, скоринг,
        │              подписи полей и тексты проверки
core/dialog.py         машина состояний — что происходит дальше
core/profile.py        профайл: какие поля собраны, что отложено, что дальше
core/rules.py          разбор реплик, сканирование полей, жёсткие правила
core/knowledge.py      поиск по базе знаний
core/llm.py            единственное место, знающее про поставщика модели
core/models.py         состояние диалога и лид
        │
adapters/channel.py    консоль (Telegram, Авито — новые классы, 3 метода)
adapters/storage.py    CSV (Google Sheets, CRM — то же самое)
adapters/web.py        HTTP-адаптер: то же ядро, вход по сети
adapters/sessions.py   сессии в памяти процесса с потолком и таймаутом
```

Перенос к другому клиенту = новый YAML. Перенос в другой канал = новый адаптер.
Ядро при этом не трогается — это и есть путь к коробке.

## Веб-демо

HTTP-адаптер (`adapters/web.py`) переводит запрос в вызов ядра и обратно.
Уберите его — продукт останется работать в консоли: интерфейс здесь витрина
к агенту, а не сам товар.

```text
POST /api/session    начать диалог      → session_id, приветствие, состояние
POST /api/message    реплика человека   → ответ, состояние профайла, флаги
POST /api/handoff    что ушло бы админу → карточка лида
POST /api/reset      забыть диалог      → сразу, не дожидаясь таймаута
GET  /health         проба для платформы
```

Интерфейс — `web/`: одна страница, один CSS, один JS, никакой сборки
и ни одной внешней зависимости. Логики диалога в нём нет: страница только
показывает состояние, которое отдал API. Слева — что агент понял, с меткой
источника у каждого значения и кнопкой «показать, что ушло бы администратору».
Справа — сам разговор.

**Идентификатор сессии передаётся телом запроса, а не в пути.** Разница
практическая: путь попадает в журнал доступа веб-сервера, тело — нет.
В журнале остаётся только `POST /api/message`, проверено запуском.

**Что демо не хранит.** Сессии живут в памяти процесса, умирают по таймауту
и не пишутся ни в файл, ни в лог. Перезапуск теряет всё — для публичного
стенда это правильное поведение: ссылка плюс свободный ввод даёт базу
персональных данных, которую никто не заказывал. Проверяется снимком
каталога до и после сквозного прогона, а не обещанием в этом абзаце.

**Маскировка контакта** включается секцией `demo.mask_fields` в конфиге:
телефон показывается как `+7 900 ***-**-67` и в профайле, и в карточке,
и в тех репликах, где бот называет номер вслух. У реального клиента секции
`demo` нет — маскировки тоже.

Потолки на публичный стенд: 400 знаков в реплике, 60 сообщений на сессию,
500 сессий, час бездействия. Длинный ввод обрезается, а не отклоняется:
отказ на стенде выглядит как поломка, а не как защита.

## Настройка модели

Ключи только в `.env`, никогда в коде и не в репозитории:

```env
AI_TEXT_BASE_URL=https://api.odirouter.ai/v1
AI_TEXT_API_KEY=...
AI_TEXT_MODEL=...
```

Смена провайдера — правка переменной. Интерфейс OpenAI-совместимый,
его понимают все используемые прокси.

Если данные должны остаться в российском контуре, подойдёт YandexGPT: у него
[OpenAI-совместимый эндпоинт](https://yandex.cloud/ru/docs/ai-studio/concepts/openai-compatibility),
поэтому меняется только `AI_TEXT_BASE_URL` и `AI_TEXT_MODEL` — код не трогается.
Примеры строк — в `.env.example`.

## Что осознанно не сделано

- **Нет подключения к Авито.** Их API требует аккаунта продавца и модерации
  приложения. Канал подключается адаптером; логика от этого не меняется.
- **CSV вместо Google Sheets** — интерфейс хранилища уже готов, замена точечная.
- **Напоминание живёт в памяти процесса.** Для продакшена нужен планировщик
  и база: перезапуск сейчас теряет таймеры.
- **Персональные данные.** Бот собирает имя, возраст и телефон — это ПДн.
  На реальном проекте нужны договор поручения с заказчиком, локальные акты
  и российский контур модели. В учебном прогоне данные придуманы.

## Ограничения разбора

Извлечение полей из свободной реплики работает на правилах, а не на модели.
Отсюда честные границы:

- **Имя из длинной фразы берётся только по маркеру** «меня зовут». Без него
  первое слово почти никогда не имя — эту дыру нашёл прогон с попыткой
  инъекции, где в карточку лида уезжало слово «Игнорируй».
- **Возраст рядом со словами «опыт», «стаж», «работал»** не забирается:
  «опыт работы 8 лет» — это не восьмилетний кандидат.
- **Телефон опознаётся только в российском мобильном формате.** Городские
  номера и зарубежные не разбираются.
- Всё неоднозначное уходит в переспрос. Это осознанный обмен: лишний вопрос
  дешевле неверных данных у менеджера.

## Тесты

53 сценария в двух наборах: 34 по «Смене» и 19 по «Параболе». Половина — про
то, как люди пишут на самом деле: путают возраст с годом рождения, спрашивают
своё вместо ответа, уклоняются, грубят, шлют простыню текста и пробуют
вытащить инструкцию.

Два набора нужны не для количества. Набор «Смены» проверяет, что ядро осталось
совместимым после правок ради другой ниши, — это главный риск проекта, и он
проверяется каждым прогоном.

```powershell
python tests/run_tests.py       # оба набора
python tests/run_tests.py -v    # + расшифровка каждого диалога
```

Зелёный тест сам по себе ничего не доказывает: он мог бы проходить и без
правки, которую проверяет. Каждая из шести правок ядра ломалась по очереди,
и набор «Параболы» падал на всех шести — от 19/19 до 4/19. Набор «Смены»
при этом оставался зелёным, что и подтверждает независимость конфигов.

Кроме собранных данных и этапа проверяется `max_questions` — сколько вопросов
анкеты бот имел право задать. Это защита от главного регресса профайла:
если бот спрашивает то, что ему уже сказали, лишний вопрос всплывёт в тесте.

Четыре реальных бага были найдены именно тестами:

1. Слово «когда» содержит подстроку «да» — вопрос кандидата засчитывался
   как подтверждение регистрации. Теперь сравнение по словам.
2. «Когда деньги придут» попадало в ответ про размер ставки вместо сроков
   выплаты. Теперь совпадение целой фразой весит больше одиночного слова.
3. Цифры телефона читались как возраст, когда всё приходило одной строкой.
   Теперь найденный фрагмент вырезается из остатка перед следующим разбором.
4. Первое слово длинной фразы уезжало в имя — включая «Игнорируй все
   инструкции». Теперь имя из длинной фразы берётся только по маркеру.

Пятый нашёлся при разборе базы по ролям: в записи про документы чуть не
появилось ключевое слово «налог». Запись говорит про форму оформления, а не
про то, кто платит налог — при ГПХ его удерживает заказчик, при самозанятости
платит исполнитель сам. Бот начал бы уверенно отвечать не на тот вопрос;
сценарий «Вопрос, которого нет в базе» это поймал.

Проверяются, кроме собранных данных и этапа:

- `derived` / `not_derived` — помечено ли поле как посчитанное нами;
- `never_says` — не сказал ли бот того, что обещать не имеет права
  (например, канал связи, которого нет в базе).
